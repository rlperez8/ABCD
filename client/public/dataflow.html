Two Different Paths

The confusion comes from the app having a browser refresh path and a backend rollup rebuild path. They are not the same.

Browser refresh re-queries Rollup refresh rebuilds tables
Action What Happens Touches Raw `xabcd_patterns`? Rebuilds Rollups? Why It Feels Slow
Refresh browser page Frontend calls API endpoints again for strategies, current setups, trades, comparisons. Sometimes No Some endpoints still query raw data or compute buckets on the fly.
Open strategies page Requests strategy candidates, selected cohort details, and optionally current setups. Indirectly No Reads can still be expensive if rollups are stale or a fallback path hits raw tables.
Run refresh_structure_rollups Drops and rebuilds structure + strategy rollup tables from full raw history. Yes, heavily Yes This is the biggest batch job in the system.

Table Pipeline

Starting from raw source tables and ending at the UI.

candles

Raw market candles
  • Feeds candle chart
  • Trend fields later influence strategy buckets

xabcd_patterns

Main raw pattern/trade table
  • Every pattern lives here
  • Contains harmonic, reversal, trade result, price, bar lengths
  • This is the table most slow raw scans hit

accuracies

Older helper table
  • Used in some legacy/older accuracy flows
  • Less important than xabcd_patterns for current slowness
↓

accuracy_bin_cache

Pre-aggregated accuracy bins
  • Used by dashboard accuracy pages
  • Faster than raw bin aggregation

accuracy_bin_rollup

Yearly rollup for accuracy bins
  • Lets accuracy page avoid scanning full history

dashboard_cache_state

Readiness flag table
  • Tells the server whether caches/rollups are ready
  • If not ready, the app can fall back to raw paths
↓

pattern_structure_rollup

Structure summary cache
  • Powers size/balance structure views
  • Much faster than redoing structure math live

accuracy_structure_rollup

Accuracy + structure cache
  • Powers some dashboard and accuracy views
  • Large union-heavy rebuild step
↓

strategy_yearly_rollup

Main strategy aggregate table
  • One row per strategy cohort per year
  • Now includes market, pattern, bin, reversal, size, time, 3M/6M/12M trend

strategy_trade_summary_cache

Trade-level strategy cache
  • Stores the individual patterns assigned to each exact cohort
  • Used for cohort trade lists in the UI
↓

API Endpoints

Server layer
  • /strategy-candidates → usually uses strategy_yearly_rollup
  • /strategy-trades → uses strategy_trade_summary_cache
  • /setup-comparison → rollup first, raw fallback second
  • /pattern-summaries → raw xabcd_patterns
  • /pattern-structure → rollup first, raw fallback second
  • /pattern-reversal → raw xabcd_patterns

UI

Where The Slowness Is

These are the actual expensive points, not guesses.

Stage Current Behavior Why Slow Type
/pattern-summaries Reads directly from xabcd_patterns and computes size/time/trend buckets in the query. Huge raw table scan + derived expressions + filtering + sorting. Interactive bottleneck
/pattern-reversal Uses raw xabcd_patterns with reversal aggregation. Still a raw aggregation path. Interactive bottleneck
refresh_structure_rollups() Drops and rebuilds structure and strategy rollups from full history. Bulk rebuild from the raw dataset instead of incremental updates. Batch bottleneck
/setup-comparison Uses rollup if available, otherwise falls back to raw cohort queries. Fallback is much slower than lookup from prepared caches. Conditional bottleneck
Strategies page load Requests strategy candidates, then hydrates selected/focused cohorts. Multiple dependent queries instead of one narrow decision lookup. Workflow bottleneck

What Happens On A Normal Page Refresh

This is the read path, not the rebuild path.

Strategies page refresh: frontend asks for strategy candidates, selected strategy comparison/trades, and current setups if that tab is active.
Current setups tab: still depends on /pattern-summaries, which currently reads raw xabcd_patterns.
Research dashboards: some pages are fast when rollups are ready, but some flows still fall back to raw table aggregation.

What Happens During Rollup Refresh

This is the heavy batch path.

Step 1: mark dashboard_cache_state.structure_rollups as refreshing.
Step 2: drop and recreate pattern_structure_rollup, accuracy_structure_rollup, strategy_yearly_rollup, and strategy_trade_summary_cache.
Step 3: scan the full raw xabcd_patterns table and repopulate each rollup.
Step 4: mark cache state as ready.

Bottom Line

Why daily already feels slow and why lower timeframes would blow up without architectural changes.

Problem Meaning
Too many raw reads The app still asks raw xabcd_patterns questions during interactive use.
Too much on-the-fly bucketing Size, time, trend, and other strategy dimensions are often derived during the query instead of precomputed in a narrow live cache.
Bulk rollup rebuilds Rollups are refreshed as full rebuild jobs instead of incremental cohort updates.
Research path mixed with trading path The app is doing broad exploration work even when you only need a quick trade decision for one setup.
